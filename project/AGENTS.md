Directories only, three levels. Regenerated by the `repo-map` skill; do not hand-edit.

application, load the `repo-map` skill and regenerate it so it matches your project.

# Always

Every prompt that changes code runs these four steps, in order:

1. **Read the reference** for what you are about to build — before the first line of code.
2. **Write the code.**
3. **Verify it at runtime** by delegating to the `verify-app` subagent. A green build is not a
   result.
4. **Sync the specs** — if `specs/` holds more than a `README.md`, update or create the story
   your change affects.

None of these is optional. "It was only a one-line change", "I only renamed a label", "I only
changed the styling" are not exemptions — those are exactly the changes whose defects survive.

Anything to do with requirements, specs or ideas: read the matching file in `harness/` first.

The detail for each step follows below.

# Dev workflow

Four steps, in this order, for **every change to code** — a new feature, a refactor, a UI
change, a one-line fix. A task is not finished after step 2, and "I only changed the
styling" is not an exemption: the defects that survive step 2 are exactly the ones that
look harmless.

## 1. Read the reference

Before writing any code, run these and read the ranges they point at:

```bash
cat docs/blazor/README.md
grep -n 'render mode\|@rendermode' docs/blazor/components-render-modes.md | head -20
grep -n 'SupplyParameterFromForm\|interactive' docs/blazor/forms-binding.md | head -20
grep -n 'Pages\|Components\|routable' docs/blazor/project-structure.md | head -20
grep -n 'DbContextFactory\|lifetime' docs/blazor/blazor-ef-core.md | head -20
```

`blazor-docs` documents the exact framework version this project runs on and is newer than your
training data. Answer these from it, not from memory:

1. Which render mode does a page need in order to handle a click, and where exactly is it
   declared?
2. What does a form need so that submitted values reach your model rather than a new instance?
3. In which folder do routable pages belong in this template, and which `_Imports.razor`
   applies there?
4. How does a component obtain an EF Core context, and what is that context's lifetime?

### If the task involves MudBlazor

Run these three as well:

```bash
cat docs/mudblazor/README.md
cat docs/mudblazor/getting-started/Installation.md
cat docs/mudblazor/getting-started/Layouts.md
```

**Project decision — settled, do not re-derive it.** This project uses **global
interactivity**. `App.razor` must contain:

```razor
<Routes @rendermode="InteractiveServer" />
```

and the MudBlazor providers — `MudThemeProvider`, `MudPopoverProvider`, `MudDialogProvider`,
`MudSnackbarProvider` — stay together in `MainLayout.razor`. If `<Routes />` carries no render
mode, add it before you do anything else.

Do **not** use per-page interactivity, and do **not** copy providers into individual pages. The
documentation allows that variant, but then every new interactive page needs its own copy, and
the day someone forgets it the dialogs fail silently while the build stays green.

Then **name every MudBlazor component you are about to write** — `MudTable`, `MudDialog`,
`MudTextField`, whatever the task needs — and read each one's file first:

```bash
ls docs/mudblazor/components/
cat docs/mudblazor/components/Table.md
cat docs/mudblazor/components/Dialog.md
```

One file per component, prose and working examples inline. Copy parameter names from those
examples. There is no API reference in this mirror, so a parameter you did not see in an
example is a parameter you are guessing — say so instead.

Installing MudBlazor is all-or-nothing: the package, the `_Imports` entry, the services in
`Program.cs`, **and** the CSS and JS tags in `App.razor`.

### If the task involves opencode itself

Config keys, agents, skills, commands, plugins, permissions, providers, MCP servers,
references — anything under `.opencode/` or in the global config:

```bash
cat docs/opencode/README.md
ls docs/opencode/
grep -n '<the feature you need>' docs/opencode/config.md
```

**Before writing any config key, check that it exists.** The schema is authoritative and
answers in one command:

```bash
python -c 'import json;d=json.load(open("docs/opencode/opencode-config.schema.json",encoding="utf-8"));print(", ".join(sorted(d["$defs"]["Config"]["properties"])))'
```

Note the outer single quotes. With double quotes the shell expands `$defs` to nothing and
the command fails with a `KeyError` — a small illustration of why a command in these rules
is only trustworthy once it has actually been run.

A key that is not in that list does nothing. It is not rejected, it is not warned about — it
sits in the file looking correct and has no effect. Measured in this project: `temperature`,
`topP` and `reasoningEffort` had been written at the top level of a config for weeks. None of
them is a valid top-level key; sampling settings belong under
`provider.<id>.models.<id>.options`, and the file had simply been doing nothing.

The same applies one level down: check the shape of a key, not just its name, before nesting
anything inside it.

### Then write the answers down

State the answers in one short list before you implement, and **for each one, name what you
will change because of it** — which file, or "nothing, the current code already matches".

Reading is not applying. An answer you write down and then do not act on is worse than not
reading at all: it costs the tokens and still leaves the defect. That is exactly what happened
here — the provider render-mode requirement was read from `Installation.md` and then ignored,
and every dialog in the app was dead while the build stayed green.

If the documentation does not answer one of the questions, say so rather than filling the gap
from memory.

## 2. Code

Implement it. Scaffold with `dotnet new blazor --interactivity Server -o <name>`, add packages
with `dotnet add package` and never by hand-editing the `.csproj`.

## 3. Verify

If you changed any `.razor`, `.cs`, `.csproj` or `App.razor` file in step 2, this step is
mandatory. Delegate to the **`verify-app`** subagent. Give it the project directory and one sentence about
what you changed:

> Verify the app in `PersonManagerApp`. I added the person list with create and delete.

It starts the application, drives a round trip against it and reports what is broken. It has an
empty context and cannot edit files, so it has no stake in your code being correct.

If you ever start a server yourself instead, keep `cd` on its own line:
`cd X && cmd > log 2>&1 &` backgrounds the whole list in a subshell that still holds the
caller's pipe, so the call blocks for the full timeout even though the redirect looks right
(measured 2026-09-16: 0.1 s vs 8.1 s for an 8-second job). Use `( cd X && cmd ) > log 2>&1 &`
or put `cd` on a separate line.

A green build is not a result. `dotnet build` proves that the code compiles and nothing else: a
Blazor page can compile, render correctly and still have every button inert, and a form can
return HTTP 302 while storing an empty record.

When the report comes back:

- Fix every defect it names, then run `verify-app` again. Do not argue with the report; it
  observed behaviour, you assumed it.
- If it reports the app did not start, that is your bug too — read the log it names.
- Only report the task as done once `verify-app` comes back clean. Pass on what it could not
  verify, in its words.

If something fails, grep `docs/blazor` for the symptom before forming a hypothesis. Your first
guess comes from the same knowledge that produced the defect.

## 4. Keep the specs in sync

Code and specs must not drift. After every change to code, walk this decision tree — in this
order, and stop at the first branch that applies.

**Does the project have specs at all?**

```bash
ls specs/
```

If `specs/` holds nothing but `README.md`, **stop here**. Do not start writing specs on your
own initiative — deriving specs from an existing application is a separate task the user asks
for explicitly.

**Otherwise, did your change alter behaviour a user can observe?**

A bug fix, a refactoring, a rename, a performance change: nothing to do. Code-only changes
never touch the specs.

**Otherwise, find the story that covers it:**

```bash
ls specs/
grep -rln '<the feature, entity or route you touched>' specs/
```

Then exactly one of these applies:

- **A story covers it** → update that story so it describes the new behaviour: the
  description, and every acceptance criterion your change affects. Add criteria for behaviour
  you added, remove criteria for behaviour you removed.
- **No story covers it, and your change introduced new user-visible behaviour** → the prompt
  opened a new story. Create it under the right epic and feature, using
  `harness/templates/Story.md`. If it belongs to a feature or epic that does not exist yet,
  create that folder too, with the next free number.
- **No story covers it and you cannot place it** → do not invent a home for it. Say so in your
  report and leave the specs untouched.

Read [`harness/_requirements.md`](harness/_requirements.md) before you write or change
anything under `specs/` — numbering, story format and the INVEST rules for acceptance criteria
are defined there.

### The `State` field

Set it from what step 3 actually established, not from what you intended:

- `verify-app` came back clean for this behaviour → `State: Implemented`
- Anything else — verification failed, was skipped, or could not cover this part → `State:
  Modified`, and name in your report what is unverified.

Never set `Implemented` on a story whose behaviour nobody observed working.

# Dev harness

Two files define how requirements and ideas are handled in this project. Reading the relevant
one is **mandatory**, not optional, and it happens **before** you write anything.

| What you are about to do | Read first |
|---|---|
| Anything to do with requirements: writing, changing, reviewing, **or deriving them from existing code** | [`harness/_requirements.md`](harness/_requirements.md) |
| Discuss a new idea, a new feature, or a larger change that has no spec yet | [`harness/_ideas.md`](harness/_ideas.md) |

```bash
cat harness/_requirements.md    # before touching anything under specs/
cat harness/_ideas.md           # before discussing a new idea
```

- Never write a story, an epic or an acceptance criterion without having read
  `_requirements.md` **in this session**. It defines the folder layout, the numbering, the
  `State` field and the INVEST rules for acceptance criteria.
- Never start implementing an idea that has no spec. `_ideas.md` defines a dialogue you run
  **first** — you are the product owner in it, you challenge the idea rather than waving it
  through, and you write no spec and no code until the idea reaches state `Ready`.
- File templates for every artefact are in `harness/templates/`.
- Specs live in `specs/`, ideas in `ideas/`. Both folders carry a README with the structure.

## Extracting specs from existing code

"Extract the specs", "document the application", "reverse-engineer the requirements" all mean
the same thing: **write spec files that describe what the application currently does.** It does
**not** mean searching the repository for spec files that already exist. If `specs/` is empty,
that is the starting point of the task, not the answer to it.

Procedure:

1. Read `harness/_requirements.md`. Everything below follows its conventions.
2. Inventory what the application actually does:
   ```bash
   grep -rn '@page' --include=*.razor <app> | grep -v obj     # routes = candidate stories
   ls <app>/Data/                                             # entities
   grep -rn 'DbSet<' <app>/Data/*.cs                          # persisted types
   grep -rn 'MapGet\|MapPost\|\[HttpGet\]\|\[HttpPost\]' <app> | grep -v obj   # endpoints
   ```
   Read each page and each entity. The source is the truth here, not the prompts that once
   created it and not your memory of the session.
3. Group the findings: one epic per coherent area, features below it, one story per page or
   per self-contained user action.
4. Write the files under `specs/` using `harness/templates/`. Create the epic folders,
   `_DataModel.md`, `_Navigation.md`, `_Backend.md` and the story files.
5. Set `State: Implemented` only for behaviour you confirmed in the code. Anything you are
   unsure about gets `Modified`, and you say so in your report.
6. Write down only what the application does. Do not invent requirements it does not
   implement, and do not silently drop behaviour you found but did not like.

When you are done, report how many epics, features and stories you created, and name anything
you found in the code that you could not classify.

# Reference

This project builds **ASP.NET Core Blazor** applications on **.NET 10**, with EF Core and
SQLite.

## Mistakes made in this project before

Every item below was produced here on 2026-09-15 and 2026-09-16, most of them repeatedly, by
models working from memory instead of from `docs/blazor`. Read this list as a description of
your own most likely output, not as a list of things other people got wrong.

1. **Pages written without a render mode.** In .NET 8 and later a Blazor Web App renders
   statically by default. Pages were written with `@onclick` handlers and `EditForm`s and no
   render mode directive, so no circuit was created: the page rendered, the buttons did
   nothing, and nothing in the build or the logs indicated a problem. Scaffolding with
   `--interactivity Server` does not apply a render mode to your pages.
2. **Forms that silently save empty records.** A statically rendered form posts back and
   rebuilds the component, so a model field initialised with `new()` is empty when the handler
   runs. Submitting `Name=Testperson, Age=42` returned HTTP 302 and stored a row with an empty
   name and age 0. It looked like success.
3. **Routable pages placed in a top-level `Pages/` folder.** The Blazor Web App template keeps
   its components elsewhere, and its `_Imports.razor` does not apply to a folder you invent, so
   every using has to be repeated per file.
4. **A missing `[Inject]`.** `LoadPersons()` threw `NullReferenceException` on page load
   because the context factory was never injected. The build was green.
5. **`Database.Migrate()` with no migrations.** The call succeeds and creates nothing, then the
   first query fails with `SQLite Error 1: 'no such table: Persons'`. Run
   `dotnet ef migrations add InitialCreate` before relying on `Migrate()`.
6. **Invented package versions.** `--version 10.0.0` was passed for EF Core packages. That
   version does not exist. Let `dotnet add package` resolve the version.
7. **`<PackageReference>` written directly under `<Project>`.** It belongs inside an
   `<ItemGroup>`. Without it every later `dotnet` command fails with `MSB4067` — including
   `dotnet add package`, so the tool can no longer repair the file.
8. **The legacy `blazorserver` template.** On this SDK it still scaffolds **net7.0** and a
   pre-.NET-8 project layout. Patching `<TargetFramework>` afterwards does not convert it.
9. **Navigation entries pointing nowhere, and no landing page.** A menu item was left for a
   page with no `@page` route, and in another run no component claimed `@page "/"`, so the root
   URL returned 404.
10. **MudBlazor providers left in a statically rendered layout.** The four providers were
    put in `MainLayout.razor`, which carries no render mode, while the pages using them are
    interactive. `Installation.md` states that static rendering is not supported for them.
    Result: build green, page renders, table shows data — and every dialog, snackbar and
    popover silently does nothing. The documentation had been read in the same session.
11. **Reporting a green build as a working feature.** In five runs the application was never
    started once. Everything above survived because `dotnet build` said nothing.
